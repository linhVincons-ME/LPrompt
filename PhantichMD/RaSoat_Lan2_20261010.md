## 2. (Trung bình) Lỗi mới: câu có phủ định bị loại cả câu, mất nội dung

**Vị trí:** `src/services/constructionPromptCompiler.ts`, nhánh `duplicate-no-media` (`continue`).

Yêu cầu bổ sung được tách câu theo `;`, xuống dòng và dấu kết câu, nhưng **không tách theo dấu phẩy**. Khi phần phủ định khớp, `continue` loại **toàn bộ câu**, kể cả phần mô tả không liên quan. Kết quả biên dịch thật:

```
"Cột điện sơn màu cam XYZQ"                     → prompt có XYZQ   ✅
"Không có âm thanh, cột điện sơn màu cam XYZQ"  → prompt MẤT XYZQ  ❌ (lỗi mới)
"Không chèn chữ, cột điện sơn màu cam XYZQ"     → prompt MẤT XYZQ  ❌ (lỗi cũ, cùng kiểu, ở duplicate-no-text)
```

Người dùng chỉ thấy một cảnh báo "đã loại khỏi yêu cầu bổ sung" và dễ nghĩ chỉ phần "không có âm thanh" bị bỏ.

**Đề xuất:** chỉ cắt cụm phủ định và giữ lại phần còn lại của câu.

```ts
if (options.outputType === 'image') {
  const withoutNegated = lower.replace(negatedMedia, ' ');
  if (mediaPattern.test(withoutNegated)) {
    issues.push({ severity: 'error', code: 'image-media-conflict', message: '...' });
  } else if (withoutNegated !== lower) {
    issues.push({ severity: 'warning', code: 'duplicate-no-media', message: 'Đã bỏ phần "không âm thanh/thời lượng" vì prompt ảnh vốn không có.' });
    // Cắt trên câu gốc để giữ chữ hoa; cờ i + u giúp khớp không phân biệt hoa thường
    const rest = fragment.replace(negatedMedia, ' ').replace(/^[\s,;.:-]+|[\s,;.:-]+$/g, '').replace(/\s{2,}/g, ' ');
    if (/\p{L}{2,}/u.test(rest)) kept.push(rest);   // còn nội dung thật thì giữ
    continue;
  }
}
```

(`negatedMedia` có cờ `g`, nên mỗi lần `replace` đều quét lại từ đầu. Không dùng nó với `.test()`, vì `lastIndex` sẽ bị giữ lại.)

Nên áp dụng cùng cách cho `duplicate-no-text`. Nên thêm test: câu "Không có âm thanh, cột điện sơn màu cam" phải giữ "cột điện sơn màu cam" trong prompt.

Tôi đã thử bản sửa này, kèm regex ở mục 3.1, trên bản sao. "Không có âm thanh, cột điện sơn màu cam" giữ được "cột điện sơn màu cam" trong prompt. "Không có âm thanh và nhạc nền" và "Ảnh không kèm âm thanh" chuyển thành `warning`. "Có âm thanh hiện trường" vẫn là `error`. Cả 62 test hiện có vẫn qua.

## 3. Điểm nhỏ nên chỉnh

### 3.1. Phủ định chưa bắt hết cách viết thường gặp

Kết quả thử:

```
"Tắt âm thanh" / "Bỏ giọng đọc" / "Không dùng thu âm" / "Không có âm thanh" → warning ✅
"Có âm thanh hiện trường"                       → error ✅
"không nhạc nền nhưng có âm thanh hiện trường"  → error ✅ (đúng, vẫn còn yêu cầu có âm thanh)
"Không có âm thanh và nhạc nền"                 → error ❌ (chỉ cắt được "không có âm thanh", còn "nhạc nền")
"Không âm thanh, có nhạc nền nhẹ"               → error ✅ (đúng)
"Ảnh không kèm âm thanh"                        → error ❌ (thiếu từ "kèm")
"Đèn chiếu sáng 10 giây một lần"                → error ❌ (lỗi cũ, nhẹ)
```

**Đề xuất:** cho cụm phủ định ăn cả danh sách nối bằng "và / hoặc / hay / dấu phẩy", và thêm vài động từ:

```ts
const negatedMedia = new RegExp(
  `(?:không|cấm|bỏ|tắt)\\s+(?:có\\s+|cần\\s+|dùng\\s+|kèm\\s+|chứa\\s+)?${mediaTerms}` +
  `(?:\\s*(?:,|và|hoặc|hay)\\s*${mediaTerms})*`,
  'giu'
);
```

(`không cần` và `không có` trong danh sách cũ đã nằm trong `không` + `(?:có|cần)`, nên có thể bỏ cho gọn.) Riêng `\d+\s*giây` thì chỉ coi là xung đột khi có "video", "clip", "thời lượng" hoặc "dài" đi kèm, hoặc hạ xuống mức `warning`.

### 3.2. Debounce có thể không bao giờ chạy nếu trang thay đổi liên tục

**Vị trí:** `extension/contentScript.ts`, `MutationObserver`.

Đây là debounce kiểu "trailing": mỗi thay đổi DOM lại đặt lại bộ hẹn 500 ms. Nếu Gemini có hiệu ứng chạy liên tục (con trỏ nhấp nháy, chỉ báo "đang suy nghĩ", stream câu trả lời dài), bộ hẹn có thể bị đẩy lùi mãi, và thông báo quá tải xuất hiện trong lúc đó chỉ được phát hiện khi trang yên. Đây là suy luận, tôi chưa đo trên Gemini thật.

**Đề xuất:** thêm thời gian chờ tối đa để chắc chắn hàm chạy ít nhất 1 lần mỗi giây.

```ts
let firstMutationAt = 0;
const observer = new MutationObserver(() => {
  const now = Date.now();
  if (mutationDebounceTimer === null) firstMutationAt = now;
  else clearTimeout(mutationDebounceTimer);
  const wait = now - firstMutationAt >= 1000 ? 0 : 500;   // maxWait 1 giây
  mutationDebounceTimer = setTimeout(() => {
    mutationDebounceTimer = null;
    // ... giữ nguyên phần kiểm tra
  }, wait);
});
```

Lưu ý thêm: code hiện tại không đặt lại `mutationDebounceTimer = null` sau khi bộ hẹn chạy. Việc này vô hại vì `clearTimeout` trên bộ hẹn đã chạy không làm gì, nhưng nên đặt lại cho rõ ràng.

Phần dự phòng đọc `lastResponse.innerText` trước khi so độ dài. Với câu trả lời rất dài, `innerText` ép trình duyệt tính lại layout. Có thể kiểm tra `textContent.length` trước (rẻ hơn), rồi mới đọc `innerText`:

```ts
if (lastResponse && (lastResponse.textContent?.length ?? 0) < 400) { const bubbleText = lastResponse.innerText.trim(); ... }
```

### 3.3. `openLPromptSideView` thiếu `.catch`

**Vị trí:** `extension/serviceWorker.ts`, handler `contextMenus.onClicked`.

`void openLPromptSideView(tab?.windowId)` có thể trả về một promise bị reject (Firefox từ chối, cửa sổ đã đóng…). `void` không bắt lỗi, nên sẽ có cảnh báo "Uncaught (in promise)" trong console của service worker. Nên viết:

```ts
void Promise.resolve(openLPromptSideView(tab?.windowId)).catch((error) => console.error('LPrompt could not open side view:', error));
```

### 3.4. Panel mở trước khi draft được ghi: rủi ro nhỏ mất đoạn bôi chọn

Do giờ panel mở trước khi ghi storage, có một khe thời gian nhỏ: panel đọc storage trước khi `set` xong, và listener `LPROMPT_DRAFT_UPDATED` đăng ký sau khi message đã gửi. Khi đó đoạn bôi chọn không hiện lên panel. Thực tế panel tải lâu hơn nhiều so với một lần ghi storage, nên khó gặp. Nếu muốn chắc chắn, panel có thể nghe `chrome.storage.onChanged` cho khóa `lpromptDraft` thay vì chỉ dựa vào message.
